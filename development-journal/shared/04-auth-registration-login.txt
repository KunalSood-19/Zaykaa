2. HOW IT WORKS
- Registration Flow: Client sends { name, email, password, phone, role } -> Controller
  validates types -> Service checks email uniqueness (case-insensitive) -> Hashes password
  via bcrypt (10 rounds) -> Stores in users.json -> Returns 201 with sanitized user & JWT.
- Login Flow: Client sends { email, password } -> Service looks up user -> Compares hash
  via bcrypt.compare -> Signs JWT with { userId, email, role } -> Returns 200 with JWT.
- Error Handling: Invalid credentials return generic 401 to prevent account enumeration.

3. TECHNOLOGIES & CONCEPTS
- Bcrypt (bcryptjs): Slow, adaptive hashing function using salt rounds; protects against
  rainbow table and brute-force attacks. Never stores plaintext passwords.
- JSON Web Token (jsonwebtoken): Compact, URL-safe bearer token encoding verified identity
  claims (userId, role) signed with HMAC SHA-256. Enables stateless authorization.
- 4-Tier Separation: auth.routes -> auth.controller -> auth.service -> auth.repository.
- Fail-Fast Environment: getJwtSecret() throws immediately if JWT_SECRET is unset.

6. VIVA QUESTIONS & ANSWERS
Q1: Why do we hash passwords with bcrypt instead of SHA-256 or MD5?
A1: SHA-256 and MD5 are fast cryptographic hashes designed for integrity, making them
    vulnerable to high-speed GPU brute-force attacks. Bcrypt is deliberately slow, CPU-intensive,
    and automatically incorporates a unique salt to prevent rainbow table attacks.
Q2: What is contained in our JWT payload and what is intentionally omitted?
A2: The payload contains public claims: { userId, email, role, iat, exp }. Sensitive data
    such as passwords, password hashes, or phone numbers are strictly omitted because JWT
    payloads are Base64Url encoded and readable by anyone who inspects the token.
Q3: Why return a generic "Invalid email or password" error on failed login?
A3: Distinct messages like "User not found" allow attackers to enumerate valid email
    addresses. A generic error ensures external attackers cannot guess registered accounts.
Q4: What is the purpose of the AuthRepository layer in our architecture?
A4: It abstracts user persistence (currently users.json via JsonStore) so that the
    AuthService contains only business logic. In CE-2, the repository can be swapped to
    Mongoose without changing the registration or login service algorithms.
