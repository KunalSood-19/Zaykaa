2. HOW IT WORKS
- On load: `app.js` calls `api.getRestaurants()` and `api.getCustomerProfile()`.
- Discovery Flow: Cards render dynamically with rating, delivery estimate, cost for two, and open/closed badges.
- Search Flow: Input triggers 300ms debounced call to `GET /api/restaurants?search=...`.
- Filter Flow: Cuisine chips trigger `GET /api/restaurants?cuisine=...`; Veg toggle triggers `isVeg=true`.
- Modal Flow: Clicking a card opens modal, fetches `GET /api/restaurants/:id` and `GET /api/restaurants/:id/menu`, grouping items into category tabs with veg/non-veg status and availability tags.
- Resilience: If the backend fails or returns no matches, friendly error retry banners or empty state resets are shown.

6. VIVA QUESTIONS & ANSWERS
Q1: Why is debouncing used for the restaurant search bar?
A1: Debouncing delays API execution until the user stops typing for 300ms. This prevents firing rapid, redundant HTTP requests on every single keystroke, reducing network traffic and backend server load.
Q2: How does the frontend communicate customer identity in Phase CE-1?
A2: The `api.js` client sends the `x-customer-id: cust_8829` HTTP header with all requests. In Phase CE-2, this will be swapped to an `Authorization: Bearer <JWT>` header without changing view code.
Q3: Why separate the API client (api.js) from the presentation components?
A3: Separation of concerns. The API client handles HTTP protocol details, base URLs, headers, and error normalization, while presentation components focus strictly on DOM manipulation and user events.
Q4: How does the modal handle restaurant menus dynamically?
A4: It queries `GET /api/restaurants/:id/menu`, receives the categorized JSON response, builds category tabs dynamically from the response data, and renders menu items with veg/non-veg indicator icons and availability status badges.
