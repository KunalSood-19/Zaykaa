2. HOW IT WORKS
- Discovery to Orders Navigation:
  * Users click the "My Orders" tab in the navbar (or visit `#orders`), which triggers `orderHistory.loadOrders()`.
  * The API helper `api.getCustomerOrders()` attaches `x-customer-id: cust_8829` and fetches private orders from the backend.
- Order Inspection Flow:
  * Clicking any order card invokes `orderDetailsModal.open(orderId)`, calling `GET /api/orders/:id`.
  * The modal derives the active lifecycle milestone from the canonical status enum, rendering the corresponding step with an animated pulsing ring while marking prior steps with green checkmarks.
- Cancellation Flow:
  * If the order status is `Placed` or `Accepted`, the "Cancel Order" button is enabled.
  * Clicking it opens a confirmation dialog. Upon confirmation, `api.cancelOrder(orderId, reason)` executes `POST /api/orders/:id/cancel`.
  * The backend verifies customer ownership and lifecycle validity, updates status to `Cancelled`, and persists the change to `orders.json`.
  * The modal updates instantly to display the cancellation banner, hides the cancel button, and automatically updates the order card badge in the background history list.

3. TECHNOLOGIES & CONCEPTS
- Multi-View Client-Side Architecture: Smooth view toggling without full page reloads, keeping cart and session state intact in memory.
- Hash-Based Deep Linking: Enables bookmarkable and shareable URLs (`#orders`, `#order-<id>`) handled entirely by Vanilla JS.
- Authorization by Design:
  * Backend endpoints strictly enforce customer ownership via `identity.middleware.js` and `orderService.js`.
  * Requests for orders belonging to another customer return `403 Forbidden` (`FORBIDDEN_ORDER_ACCESS`), preventing cross-customer data leakage.
- Accessible ARIA Patterns: Modal backdrops, `role="dialog"`, `aria-modal="true"`, focusable cards, and keyboard dismiss (`Escape`).
- Pure CSS Micro-Animations: Pulsing active timeline dots (`@keyframes pulse`), shimmer skeleton loaders, and rotating refresh spinners without external libraries.

6. VIVA QUESTIONS & ANSWERS
Q1: How does Zaykaa prevent a customer from inspecting or cancelling another customer's order?
A1: Authorization is strictly enforced at the backend service layer (`orderService.js`). When `GET /api/orders/:id` or `POST /api/orders/:id/cancel` is called, the server resolves the authenticated customer's identity from `req.user.id` and compares it against `order.customerId`. If they do not match, the request is immediately rejected with HTTP `403 Forbidden` (`FORBIDDEN_ORDER_ACCESS`). The frontend also only requests `GET /api/customers/orders`, which scopes queries to `req.user.id`.

Q2: Why is order cancellation restricted to specific lifecycle states?
A2: In a food delivery platform, kitchen resources and preparation time cannot be recovered once cooking begins. According to our domain contract, cancellation is permitted only while the order is in `Placed` or `Accepted` status. Once the kitchen transitions the order to `Preparing`, customer cancellation is rejected with HTTP `400 Bad Request` (`ORDER_CANNOT_BE_CANCELLED`).

Q3: How is the visual status timeline kept honest and in sync with backend data without fake GPS tracking?
A3: The timeline derives its active milestone directly from the canonical status enum returned by the backend (`Placed`, `Accepted`, `Preparing`, `Ready for Pickup`, `Out for Delivery`, `Delivered`). We deliberately do not simulate fake real-time GPS locations or fabricate transit coordinates; instead, the customer has a manual "Refresh Status" button to retrieve verified server updates.
